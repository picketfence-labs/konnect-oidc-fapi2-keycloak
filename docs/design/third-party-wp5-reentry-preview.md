## Diagnostic behavior

Set `FAPI_DEMO_AS_PEER_REENTRY_PROBE=true` only for the re-entry proof run. The existing `FAPI_DEMO_AS_PEER_OBSERVER` OFF guard remains first. The probe stores a request-local tuple only after the method, raw path, endpoint, and correlation ID match the fixed allowlists. A duplicate handler invocation emits `WP5_AS_PEER_REENTRY` with that tuple and counts from 2 through 16. The next invocation emits the fixed `count_limit_exceeded` error. Unknown paths and invalid correlation IDs produce no probe record.

The diagnostic does not read the body, query, token, headers, or certificate a second time. It does not change the observer's 13-field row, certificate checks, OAuth handling, or HTTP response. Probe failures remain isolated from the existing marker handling.

## Runtime acceptance

The isolated proof uses three fresh Keycloak starts and one direct TLS PAR POST per mode: observer on / probe off, observer on / probe on, and observer off / probe on. The first mode requires exactly one healthy `WP5_AS_PEER_OBS` row and zero re-entry rows. The second requires that same healthy peer evidence plus a same-correlation-ID PAR re-entry sequence starting at 2 and continuing contiguously through at least 2. The last mode requires zero rows from both marker families. Each POST uses a distinct 32-character correlation ID, the same fixed non-secret body, and the same valid Route B client certificate. All three responses must be the same accepted OAuth-negative status, 400 or 401. Readiness uses a fixed unregistered GET path and must not create marker rows.

These checks prove handler re-entry for this exact PAR request and configuration. They do not claim OAuth success, stock Kong behavior, new-listener negative coverage, or the broader v3 runtime matrix.
